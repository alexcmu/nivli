# Pairing and device sessions

Ticket 01 implements identity only. Public contracts are generated from trusted TypeBox route schemas in [openapi.json](../contracts/openapi.json). Reminder creation, notification registration, model processing, and synchronization are unavailable and are not advertised as capabilities.

The administrator secret is supplied through a file (`ADMIN_SECRET_FILE`), independently from device credentials. Use at least 32 unpredictable characters. `PUBLIC_URL` must be an HTTPS origin; configure a trusted TLS proxy. Mobile clients validate the certificate, reject URL credentials/query/fragments, and confirm the host, environment name, push mode and model data destination before sending any pairing credential.

`POST /v1/admin/pairings` requires administrator Bearer authentication, an empty JSON object and a UUID `Idempotency-Key`. It produces a cryptographically random 12-character code, valid for five minutes, with atomic single consumption. Codes are stored as SHA-256 digests. Repeated identical administrator requests recover the original code; response data is encrypted with AES-256-GCM using a key derived from the administrator secret.

`POST /v1/pairings/claim` accepts `{code, deviceName}` and a UUID `Idempotency-Key`. Only one non-revoked primary device is allowed. The server creates an owner-scoped device/session in the same transaction that consumes the code. A lost response can be recovered using the identical code/body/key, until its access credential expires or is invalidated. Reusing the key with different contents produces `409 IDEMPOTENCY_CONFLICT`; consumed, expired and unknown codes produce the same `401 PAIRING_REJECTED`. Replacing the primary device requires an administrator to revoke the old device first. Revocation does not guarantee removal of data or system requests on an offline phone.

Access tokens expire after 15 minutes. Refresh tokens expire after 30 days. Both are random 256-bit opaque tokens stored as digests. `GET /v1/session` verifies owner, device and session identity, expiry and revocation. `POST /v1/session/renew` accepts `{refreshToken}` with a UUID `Idempotency-Key`, rotating both tokens atomically and extending the refresh window. Retries using the same request recover the response while the resulting token remains current; old tokens are invalid after rotation. Expired credential response retries return `410 CREDENTIAL_RESPONSE_EXPIRED`. Idempotency records last at least 90 days; older retries are rejected rather than treated as new operations. Changing the administrator secret makes old encrypted retry responses unreadable, while independently hashed live device tokens remain verifiable.

`DELETE /v1/session` with a device access token and UUID `Idempotency-Key` revokes that session; subsequent authenticated calls fail. A retry with the original token and same key can recover the revocation response while that token remains within its original expiry window; a fresh revocation key cannot reuse the revoked identity. `DELETE /v1/admin/devices/{id}` with administrator authentication and a UUID `Idempotency-Key` revokes the device and all its sessions, allowing a new primary pairing. Identical revocation retries return the saved result; changing the device ID under the same key returns 409. No public endpoint creates an administrator. There are no push bindings in this ticket; dependent notification work must check this device revocation boundary when establishing bindings.

Pairing, renewal and administrator requests each have durable, atomic limits of ten attempts per IP per 60-second window, including failed authentication. Counters persist across API restart and are shared across processes. The proxy's claimed forwarding address is not trusted: the directly observed peer is the limit key. With a proxy, this intentionally shares the budget across callers. Failures return `429 RATE_LIMITED`, allowing retry after the window. Pairing TTL can be varied between 1 and 600 seconds only through the programmatic test/config boundary.

Every API failure returns `{code,message,requestId,retryable}`. Validation details, credentials, raw requests and exception stacks are excluded. Routine request logging is disabled; process diagnostics contain only status descriptions. Tokens and pairing codes must never be placed in URL query parameters, shell history, screenshots, or support logs. Native credentials are stored in Keychain and are not exported into application defaults.

## Verification

The HTTP suite uses a fresh PostgreSQL database per execution and exercises the real Fastify listener, Drizzle transactions and pg-boss schema. It covers unauthenticated requests, secure code creation, atomic concurrent claim, primary replacement, recovery retries, rotation, expiry, revocation, rate-limit persistence across restart, strict validation and log privacy. Test clock advancement is at the environment boundary; the database and queue are not mocked. Tests require a disposable PostgreSQL superuser that can create/drop fixture databases, never a production database.

CI executes the same suite, regenerates OpenAPI and rejects contract drift. Native DTO/UI evidence is recorded separately under `ios/`. Queue processes connect to real pg-boss and record heartbeats; ticket 01 does not claim that reminder or model consumers have been implemented.

# Nivli UI 设计方案

设计提案 v1 · 2026-10-11 · 基于 PRD v0.3

配套：[可点击 UI 原型](./nivli-ui-prototype.html) · [技术选型](./nivli-architecture.md) · [技术方案 HTML](./nivli-architecture.html)

这是一份可进入 SwiftUI 实现阶段的体验与视觉方案；HTML 用于评审流程和信息层级，不是 iOS 系统控件的像素级复刻。页面里的数据、通知、授权与连接均为演示。

## 1. 产品判断：方向成立，但六个问题需要先解决

### 1.1 首版范围偏大，应该分阶段验收

时间提醒、地理围栏、邮箱、长期记忆、自托管分别都涉及信任和恢复问题。保留 PRD 的完整首版目标，但按三个可独立验证的里程碑开发：A 自己交代 → 确认 → 本地时间提醒 → 完成；B 地点提醒与端侧授权；C 一个邮箱来源 → 建议 → 确认 → 提醒。A、B 是内测，只有 C 也通过才称为 PRD 所述完整首版。暂不加入灵动岛、电话、多 agent 分工或复杂富媒体通知。

### 1.2 记住与提醒就绪，不能混为一句“好的”

创建结果需要分开表达“已保存”和“提醒已安排”。例如“已记下 · 明天 09:00”下面显示“本机提醒已安排”；权限关闭则显示“已记下，开启通知后才能提醒你”。网络不可用时显示“保存在此 iPhone · 待同步”，不声称后端已经收到。页面层级只显示可行动的异常，详细技术状态放进环境页面。

### 1.3 建议不是任务，也不是已确认的记忆

首页 AI 建议独立分组“待你确认”，使用“这封邮件似乎需要补交材料”而不是“你需要补交材料”。没有完成圆圈；只有“设为提醒”“不用了”和来源。接受后才出现正式任务。冲突信息进入建议而不是覆盖旧承诺。

### 1.4 “出门前”需要降级预期

系统检测到离开一个区域，可能已经走出一段距离。界面用“离开家附近时”，详情解释“地点提醒可能延迟；如果一定要出门前带上，可以另设出发时间”。首次输入“出门带硬盘”时，先确认“家”或出发时间，不把地理围栏宣传成门口传感器。位置拒绝后仍可设时间提醒。

### 1.5 通知内容与隐私存在真实取舍

默认锁屏显示“你有一件待处理的事”；任务细节在解锁进入详情后查看。用户可主动选择显示详情。Apple 也提供系统预览控制，但应用自己的隐私选择必须落实到通知内容，不能只依赖系统默认。保守模式下不要允许在缺少上下文时误完成事项：进入详情或要求认证后再处理。演示原型可切换两种模式。[Apple 通知指南](https://developer.apple.com/design/human-interface-guidelines/notifications/)

### 1.6 自托管安装是产品体验的一部分

应用第一次打开先连接个人环境，支持扫描服务端配对码或输入 HTTPS 地址、一次性配对码。连接页展示主机和“谁能处理你的内容”；配对成功后直接交代第一件事。官方 iOS 包远程推送需要发行方中继，而自行签名可自带 APNs 凭据；这不是 Docker 能自动解决的事，详见技术方案。

## 2. 体验主张

**打开时一眼明白，放下后放心交给它。**

设计从一条提醒开始：用户要做的动作是视觉中心。极简意味着减少决策数量，同时保留来源、状态和修正入口。伙伴感来自准确的记忆和有分寸的文案。

三个长期稳定的顶层入口：

- **此刻**：该关注什么。分为接下来、稍后、待你确认；“全部”进入所有事项与已完成记录。
- **交代**：说新事、补充上下文、修改旧事。聊天是输入方式，任务确认卡是结果。
- **我的**：它知道什么、何时提醒、使用哪套环境。记忆、来源、提醒设置和数据控制集中在这里。

不添加独立的“AI”“发现”“记忆库”顶层标签，不在 tab 上放创建动作。Tab 只承担导航，三个页面各自保留滚动和导航状态。[Apple Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)

## 3. 视觉方向与设计取舍

### 3.1 紧凑设计系统

- 画布：浅色 `#F5F5F7`，深色 `#000000`。
- 内容面：浅色 `#FFFFFF`，深色 `#1C1C1E`。
- 主要文字：浅色 `#1C1C1E`，深色 `#F5F5F7`。
- 次要文字：浅色 `#63636B`，深色 `#A9A9B2`。
- 动作蓝：浅色 `#0066CC`，深色 `#78B4FF`。
- 分隔线：浅色 `#E5E5EA`，深色 `#38383A`。

这些是 HTML 评审色值；SwiftUI 实现优先采用 `.primary`、`.secondary`、系统 background 与可访问的 tint，随系统外观调整。危险操作使用系统 red，只出现在确认删除等场景。

字体采用系统字体：中文由系统匹配苹方，英文 SF Pro；不捆绑字体。SwiftUI 使用语义 text styles，而不是硬编码字号。基准：大标题 34 pt、标题 22 pt、正文 17 pt、辅助信息 15 pt、极少量时间标记 13 pt。中文正文行高约 1.45，阅读区左对齐。

布局基准：393 pt 逻辑宽度；两侧 20 pt；组间 28–32 pt；内容内部 12–16 pt。事项以开放列表为主，唯一需要突出的大块面留给下一件事；建议因未确认而单独成组，不做满屏同构卡片。原生页面遵循 safe area，底部导航不会遮住最后一行。

### 3.2 方案自检与修订

初始想法是将“聊天输入框”常驻所有页面。审视后去掉：它与独立的交代页重复，并挤占小屏上的事项空间。另去掉首页统计、AI 动态头像、完成率和自动轮播，保留一条短摘要和直接动作。

玻璃效果只属于顶层导航与瞬时控件。内容保持清楚的实色背景。实际 SwiftUI 使用系统 TabView、toolbar、sheet 自动适配 Liquid Glass，不在每个内容卡片自绘 blur；HTML 仅近似层级。[Apple Materials](https://developer.apple.com/design/human-interface-guidelines/materials) · [Adopting Liquid Glass](https://developer.apple.com/documentation/TechnologyOverviews/adopting-liquid-glass)

## 4. 页面与交互规格

### 4.1 此刻

从上到下：日期；大标题“此刻”；“全部”入口；下一件明确提醒；稍后的时间或地点任务；独立的“待你确认”。排序先处理已到提醒时间的事项，再按近期时间、可用情境排序。没有明确时间的地点提醒不要伪装成今天必然发生。

每项主要展示动作、提醒条件、必要截止时间；来源摘要按需出现。完成按钮有至少 44×44 pt 热区，详情行和完成按钮是两个独立可访问控件，不嵌套。完成立即移出待办，出现“已完成 · 撤销”，撤销恢复原状态。推迟只修改下一次提醒，不修改截止时间。

空状态：“暂时没有要处理的事。想到什么，可以随时交代。”保留交代入口，不制造内容。已安排的以后事项和待确认建议仍可以找到；完全空状态只用于确实都没有时。

### 4.2 交代

文本输入框贴近键盘，Enter 发送、Shift+Enter 换行；SwiftUI 使用系统键盘与焦点管理。语音是后续能力，本版不放一个无法使用的麦克风。

明确交代可直接创建并提供可撤销确认卡：“给绿植浇水 · 10 月 11 日 09:00 · 本机提醒已安排”。卡片有“修改时间”。自然语言不足以确定目标时追问，例如“你想修改提交材料，还是补交附件？”不靠置信度百分比让用户理解错误。

处理中显示轻量行内状态；失败保留输入并提供重试与手动设置。一个“发送成功”的气泡不代表提醒成功。聊天中显式结果标签区分“已设提醒”“已记住”“仅在本次对话使用”。修改和删除会更新关联卡片，旧卡片标为“已更新”并指向最新状态。

HTML 的文本解析仅为有限演示；预置示例能完整走通。其他文本进入明确标注的手动确认，不假装连着真实模型。

### 4.3 事项详情

大标题是要做的动作；下一行是状态。下面依次为提醒条件、截止时间、来源和“为什么现在提醒”。修改时间通过 sheet，表单保存前展示完整日期和时区。当前状态从本地投影与服务端版本对齐，旧通知进入后展示新状态，不重新创建任务。

底部操作：完成、稍后提醒；取消事项在更多操作内。删除与完成是不同动作。重要异常贴在对应条件下，例如“家已被删除，请选择地点或改用时间”。

### 4.4 邮件建议

使用“待你确认”标签。展示建议动作、推测截止时间、简短原文依据、发件人和日期。默认折叠邮件正文，不从列表泄漏整段内容。主按钮“设为提醒”打开可编辑时间的确认表单；辅助按钮“不用了”。忽略之后支持撤销，一次忽略不会生成“永远不提醒这类邮件”的偏好。

邮件里已有日期变化时，展示旧、新两种安排和“保留原安排 / 更新安排”。未经确认，旧任务的时间不变。同一邮件线程的建议被接受后，后续邮件进入同一任务的变更建议。

### 4.5 我的

顶部显示个人环境简名和当前可用状态。默认正常时不显示 API、模型步数、token、queue 等调试信息。

- 记忆：你确认的地点、习惯；待确认推测放单独区域。点入可以修改、忘记和查看来源。“这次不要记住”作用范围明确。
- 信息来源：邮箱账户、访问范围、最近同步时间；断开授权和删除历史衍生数据分开。
- 提醒方式：安静时段、建议频率、锁屏预览；明确交代与 AI 建议分别设置。
- 数据与环境：导出、删除、服务地址与连接检查；高级模型设置置于二级页面。

系统通知关闭时展示“提醒已保存，但通知已关闭 · 前往设置”；禁止用开关伪造系统授权。位置权限只在创建位置提醒时申请；优先采用系统 `UNLocationNotificationTrigger` 所需的最少授权，不因为产品叫“主动 AI”就索取持续位置。[Apple 位置通知](https://developer.apple.com/documentation/usernotifications/unlocationnotificationtrigger)

### 4.6 首次连接

“连接你的 Nivli” → HTTPS 服务地址 + 一次性配对码 → 确认主机和数据处理方 → 连接成功 → 第一件交代。扫码是等价入口，实现时不跳过主机确认。配对码不能是长期 API 密钥，二维码和日志不能包含模型密钥。

模型凭据由服务器管理员配置。首次部署网页负责基础模型测试，iPhone 遇到配置缺失可手动设提醒并指向环境详情。通知权限在第一条提醒保存时由用户触发；邮箱与地点在相应需求出现后再申请。

## 5. 通知是核心界面

普通通知由 iOS 管理布局，应用提供标题、正文、category 和操作，不自定义锁屏外壳。HTML 中展示的锁屏是说明性示意，不能承诺按钮在折叠态直接可见。

- 默认保守：“Nivli / 你有一件待处理的事 / 解锁后查看详情。”
- 已允许详情：“提交材料 / 今天 18:00 截止，可以先检查附件。”
- 展开并满足认证条件后操作：“完成”“30 分钟后”。点通知本身进入详情，因此不再增加重复的“查看详情”动作按钮。
- AI 建议默认进入应用内待确认区；用户主动开启建议通知后，按摘要节奏发送，不把每封邮件推到锁屏。

这遵循 Apple 对简洁内容、直接操作和避免重复通知的建议；未响应不触发自动升级。[Apple Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications/)

安静时段默认 22:00–08:00 作用于 AI 建议。用户明确设在安静时段的提醒，创建时提示“这是安静时段，仍按 23:00 提醒？”这个确认不代表可以绕过系统 Focus。普通提醒使用 active；仅符合即时性且用户允许时用 Time Sensitive；首版不申请 Critical entitlement。[Apple Managing notifications](https://developer.apple.com/design/human-interface-guidelines/managing-notifications)

## 6. 必须设计的异常与恢复

- **无法连接**：已有本机提醒继续保留；新修改标为“此 iPhone 已更新 · 待同步”。提供重试，不弹全屏错误。
- **模型不可用**：保留用户原话，允许用日期与标题手动保存。
- **通知关闭**：显示受影响的事项和前往系统设置入口；不显示“提醒已就绪”。
- **位置不可用**：条件旁解释原因，直接提供时间替代；不静默变成时间提醒。
- **邮箱授权过期**：停止读取并提示重新连接；已确认任务保留，建议标注来源可能过时。
- **冲突**：保留双方修改，向用户呈现差异；完成与取消优先阻止旧通知继续操作，但明确恢复应创建新版本。
- **删除记忆**：说明哪些记录会删除，是否保留用户确认的任务；对无法立即清除的备份说明保留窗口。遗忘后检索索引与摘要也需更新。
- **无内容**：留白与一条交代入口，不用鼓励性压力文案。

## 7. SwiftUI 落地

建议最低 iOS 26，采用当前系统控件；若目标用户设备需要 iOS 18，再降低 deployment target 并使用 availability 分支，不用网页视觉倒推自绘 TabBar。该最低版本是产品取舍，需用首批用户设备分布确认。

`TabView` 承载三个 `NavigationStack`；`List`/`Section` 用于事项与设置；`sheet` + `presentationDetents` 用于时间与来源；`DatePicker` 使用语义标签与完整日期；`ContentUnavailableView` 用于完全空状态；`safeAreaInset` 管理输入区；SF Symbols 使用系统图标。HTML 图标是示意线稿，不作为 SF Symbols 资产分发。

使用 Swift Observation 管理屏幕状态，独立 repository 管理本地 SQLite 投影、待同步操作和网络。View 不直接调用 agent。确认任务有稳定 ID；Task 与 Suggestion 是不同类型；状态不会靠文案字符串推断。

无障碍验收：至少 44 pt 操作热区；正文至少 4.5:1 对比目标；VoiceOver 朗读“提交材料，今天十点提醒，未完成”；动态字体到 accessibility sizes 时改纵向操作布局；颜色不独立编码状态；Reduce Motion 禁用大幅位移；Reduce Transparency 使用实色；暗色独立检查。上述热区与适配遵循 [Apple Design Tips](https://developer.apple.com/design/tips/) 和 [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)。

## 8. 评审方式与交付边界

打开 HTML，在左侧切换“此刻、交代、事项详情、邮件建议、我的、首次连接、空状态、离线”；可以完成并撤销、推迟、创建演示提醒、接受/忽略建议、切换隐私预览、切换深色及大字模式。右侧同时解释当前页面的设计理由。

设计验收建议找 5–8 位目标用户做任务测试，目标不是宣称现有验证结果：首次无需提示找到交代入口；区分建议与任务；找到来源；知道断网时哪些提醒仍有效；从通知处理任务。记录实际耗时、误操作和误解，再决定是否保留三个 tab。HTML QA 只能验证交互原型；真机通知、权限、VoiceOver 和后台行为必须在 SwiftUI 阶段验证。
